# spfy GUI

A desktop app for picking a voice, typing or pasting text, hearing it, and
saving the WAV. Windows, macOS and Linux, and usable with a screen reader.

```
spfy/gui/
  package.json  package-lock.json   npm is only here for @tauri-apps/cli
  web/                              the whole front end; static files, no bundler
    index.html  index.js  styles.css
  src-tauri/
    Cargo.toml  Cargo.lock  build.rs  tauri.conf.json
    capabilities/default.json
    src/main.rs      list_voices / list_available / install_voice / synth /
                     save_wav, plus --self-check
    icons/           32x32.png  128x128.png  128x128@2x.png
                     icon.png  icon.ico  icon.icns
  linux/install-desktop.sh          writes the .desktop entry at run time
  macos/Info.plist.in               template for Speechify.app
```

The icon set is not optional and not decoration. See "Four things that were
not obvious" below.

## Build and run

```powershell
cd spfy\gui
npm install                 # one-time; pulls @tauri-apps/cli only
npx tauri dev               # run it
npx tauri build             # exe in src-tauri\target\release\spfy_gui.exe
```

A release build does not need npm at all, and CI does not use it:

```powershell
cargo build --release --locked --manifest-path spfy\gui\src-tauri\Cargo.toml
```

There is no bundler and no `beforeBuildCommand`. `frontendDist` is `../web`,
which is static files already in the repo, and `bundle.active` is false, so
`tauri build` and `cargo build` produce the identical binary; the former just
routes through Node to get there. npm stays useful for `tauri dev` (hot
reload), which is why `package.json` is still here.

Verified from a clean tree holding only the committed sources: 2m26s, and
`src-tauri/gen/schemas/` regenerated by `tauri-build` as expected. That
directory is gitignored on purpose.

The app needs `spfy_synth` at run time. In a dev tree, point at your build:

```powershell
$env:SPFY_SYNTH = "C:\tmp\spfy_build32\src\cli\spfy_synth.exe"
npx tauri dev
```

## Three decisions, and why

### 1. Tauri, a webview rather than a native-widget toolkit

Accessibility is the entire reason. Immediate-mode GUI libraries (Dear ImGui,
Nuklear, raylib, FLTK) paint their own pixels and expose nothing to UIA,
AT-SPI or NSAccessibility: to a blind user the window is empty. A webview
exposes the DOM, so the platform's screen reader sees real controls for free.
This is a speech synthesizer. A meaningful share of its users run NVDA,
Narrator or Balabolka, and an inaccessible GUI here would be worse than none.

It also wins on the hardest thing on the feature list: a tag- and phoneme-aware
editor with highlighting, an insert palette and validation is close to free in
HTML and is hand-built work in every native toolkit.

Tauri uses the OS webview (WebView2, WKWebView, WebKitGTK), so the shipped
binary is 3.5 to 3.8 MB depending on architecture, against roughly 150 MB for
the equivalent Electron app.

### 2. The GUI never links the engine. It spawns `spfy_synth`

Measured 2026-08-23, warm cache, whole process, voice load through WAV write:
70 to 114 ms for tom, 94 to 140 ms for the 152 MB crstom, 138 ms for a full
bulletin sentence. Under the ~200 ms where a UI starts to feel slow.

This is not only a convenience. The engine is one synth per process:
`spfy/src/cli/spfy_synth.c` carries 76 file-scope statics and `src/host_emu`
keeps global guest state for the emulated front end. Do not plan on two
concurrent synths inside one process.

It also keeps the byte-exactness claim honest. The GUI hears exactly what the
CLI, SAPI, the WASM build and the CI gate produce, by construction.
`spfy_sapi64.dll` already works this way.

### 3. Forked from `spfy/wasm/web/`, not shared with it

The WASM demo is deployed elsewhere (GitHub Pages, EAS Tools), so it has to
keep standing on its own and the desktop app must never be able to break it.
The cost is accepted knowingly: the editor, palette and highlighting exist
twice. The backends have little in common anyway. The demo calls
`spfy_wasm_synth()` in its own address space and reads int16 PCM out of
`HEAP16`; this one gets a whole WAV file back from Rust and uses
`decodeAudioData`.

## Why `bundle.active` is false

`tauri build` stops at `src-tauri/target/release/spfy_gui.exe` and does not
produce an installer of its own.

The app ships inside `installer/spfy_setup.iss`, landing in `{app}` beside
`spfy_synth.exe`, which is exactly how it finds the engine. Tauri's own NSIS
bundle would be a second, competing installer shipping the shell without an
engine, so a user who ran it would get a window that cannot speak.
`iscc /DWithGui` picks the exe up from the cargo release directory instead.

Flip it to true only for a standalone build on a platform Inno does not cover,
and then make the engine a Tauri sidecar first, or you ship the same broken
thing.

`tauri.conf.json` rejects unknown keys, so this note cannot live in the file it
describes. Changing `active` means changing this section too.

## How it finds `spfy_synth`

1. `$SPFY_SYNTH`, if it points at a real file. How a dev checkout works.
2. Beside this executable. How the shipped install works: `spfy_setup.iss`
   puts `spfy_synth.exe` in `{app}` and drops `spfy_gui.exe` there too, and
   the macOS bundle carries both in `Contents/MacOS`.
3. Bare name on `PATH`.

If none of those hit, the window shows the path it tried and what to set. That
error and the no-voices notice are the two first-run states worth getting
right. Voices are 66 to 222 MB and only tom is bundled, so a short voice list
is the normal first run rather than a failure. The app says where voice folders
go, offers Rescan, and offers "Get voices..." to download more.

## Text goes through a file, never argv

`synth()` writes the text to a temp file and passes `-f`.

On Windows `argv` arrives in the ANSI code page, so anything non-ASCII loses
every byte above 0x7F before `main()` sees it. Silently, with no error,
producing the wrong phonemes. An accented character or an SSML `<phoneme>` with
an IPA `ph` attribute both hit this. `-f` reads UTF-8 and UTF-16 LE correctly.

Every spawn also passes `--silent`, so nothing but a real error reaches stderr,
and whatever does turn up there is shown to the user verbatim.

## The insert palette

Five tabs above the editor: Voice, Pauses, Emphasis, Say as, Phones. Each
inserts real, working notation for this engine. Everything in them is either
SSML (translated by `spfy/src/common/ssml.c`) or a Speechify User's Guide `\!`
tag (handled by `spfy_etags_resolve()`). Nothing is invented.

Templates use two markers. `$S` is where the current selection goes; `$C` is
where the caret goes instead, for tags whose interesting field is an attribute,
such as `<sub alias="...">` and `<phoneme ph="...">`. With nothing selected the
caret lands where `$S` was, so you insert `<prosody rate="slow">` and are
already typing inside it.

Selecting text first wraps it. Inserting always returns focus to the editor, so
you insert and keep typing rather than tabbing back.

`insertText()` uses the function form of `String.replace`. The string form
treats `$&`, `$'` and `$1` in the replacement as substitution patterns, so
wrapping a selection containing a dollar sign would silently mangle it.

Phone chips are context-aware. Inside an open `\![...]` block a chip inserts
the bare character, extending the word you are building; outside one it inserts
a whole `\![.1x]`. ToBI blocks share the `\![` opener and are excluded by name,
because dropping a stray `k` into `\![ToBI:H*]` would produce a tag the engine
speaks out loud.

The palette collapses, and remembers. 43 phone chips are the right thing to
have within reach and the wrong thing to look at all day.

## Visual direction

An instrument panel for a speech machine, not a web page.

The subject is a reproduction of a 2003 SpeechWorks concatenative engine, and
its vernacular is notation: `\![.1hE.0lo]`, ARPAbet, ToBI accents, sample
counts. So the personality lives in typographic treatment: monospace for
everything the engine reads or writes, wide-tracked micro-labels the way a
hardware panel legends its controls. That is a constraint as much as a
preference. `default-src 'self'` and an offline app mean there is no web font
to load, so system stacks are all there is and the type has to earn its
character some other way.

One accent, one meaning. A broadcast amber that means sound: the Speak button,
the tally dot while audio plays, the level-meter mark beside the wordmark.
Nowhere else. Focus is a separate cool blue on purpose, because "focused" and
"playing" must never look like the same state.

The signature is the phone grid: the SPR character large, its ARPAbet name
small underneath. Every other TTS front end labels a phoneme by its ARPAbet
name. Here the SPR char is primary because it is what you actually type inside
`\![...]`, and this alphabet is specific enough to this engine that showing it
is the point.

Case is semantic. `a` is aa (father), `A` is ae (cat); `i` is iy, `I` is ih.
Nothing near those chips may `text-transform`, and the face has to be the
monospace one so the two cases stay distinct.

Both themes are visually verified, not just written.

### Two CSS traps this file already hit

* `[hidden]` loses to any author `display`. `.panel { display: flex }` silently
  defeats the UA sheet's `[hidden] { display: none }`, so every tab panel
  rendered at once and the editor was pushed off the bottom of the window.
  `.panel[hidden]` and `#palette-body[hidden]` exist for that reason.
* `button:hover:not(:disabled)` scores 0-2-1 and beats a plain `.primary` or
  `.tab[aria-selected="true"]`. That is why the hover rules are written at
  matching specificity rather than as simple `.primary:hover`.

## Accessibility rules this code holds itself to

* Every control is a native element with a real `<label for>`. No div-buttons,
  no `role="button"` on a span, no placeholder standing in for a label.
* Status goes through `aria-live="polite"` so results are announced, not just
  drawn. Errors use `role="alert"`, which is assertive, because they stop work.
* Focus rings are never removed, only replaced with a louder one.
* State is never signalled by colour alone.
* `prefers-color-scheme` and `prefers-reduced-motion` are honoured.
* A skip link is the first tab stop.
* Ctrl+Enter speaks, Escape stops. Not bare Enter: the WASM demo uses that, but
  there the textarea is a one-liner. Here it is a full editor holding SSML, and
  a newline has to be a newline.
* The tab strip uses roving tabindex: one Tab stop for the whole strip, with
  arrows, Home and End moving within it. Tabbing through 43 phone chips to
  reach the editor would be hostile.
* Tabs and panels are generated from one table, so a tab, its panel, and the
  `aria-controls` / `aria-labelledby` pair between them cannot drift apart.
* A phone chip's visible text is two cryptic codes, so its `aria-label` carries
  the example word sighted users get from the layout: "E, ARPAbet eh, as in
  dress".
* `localStorage` reads and writes are wrapped in try/catch. It throws, rather
  than returning null, in a webview with site data blocked, and an exception
  there would abort the rest of start-up.
* `color-scheme` is declared for both themes, so the native `<select>`
  dropdown, both scrollbars and the caret match. CSS cannot reach those.

## Not built yet

* Highlight-as-it-speaks, via the `SPFY_WORD_EVENTS_FILE` and
  `SPFY_PHRASE_EVENTS_FILE` sidecars. They carry sample offsets, so no linking
  is needed. This is the big one.
* Validation of the notation as you type. The insert palette exists and is
  described above; what is missing is telling you a tag is wrong before you
  press Speak.

## Platforms

Every desktop artifact except the two static-musl tarballs ships the GUI.

|-----------------------|-----|-------------------------------------|---------------------|
| Windows x64 installer | yes | cargo build, host triple            | Start Menu, AppPaths|
| Windows x86 installer | yes | --target i686-pc-windows-msvc       | Start Menu, AppPaths|
| linux-x86_64          | yes | debian:bookworm container           | install-desktop.sh  |
| linux-x86             | yes | i386/debian:bookworm container      | install-desktop.sh  |

Built locally and verified: both Windows arches (self-check passes on each),
linux-x86_64, linux-x86 and linux-armv7, all three Linux binaries referencing
no glibc symbol above 2.34 against a 2.36 ceiling. linux-arm64 and the two
macOS legs are wired but were first exercised in CI; arm64 runs the identical
image and script as linux-x86_64.

### Four things that were not obvious

**`icons/icon.png` is required, and only Linux says so.** `tauri.conf.json`
listed `icon.ico` alone, which is a Windows format. `generate_context!` then
fails to compile on Linux with `failed to open icon icons/icon.png`. One
Windows-only icon is the reason this had never built anywhere else. The full
set is committed now, and `icon.icns` is what makes `Speechify.app` show a real
icon rather than a blank page in the Dock.

**rustup derives the host triple from the kernel, not the userland.** In an
i386 container on an x86_64 host `uname -m` says `x86_64`, so rustup installs a
toolchain the 32-bit userland has no loader for, and every command then dies
with `command failed: 'rustc': No such file or directory` against a file that
is plainly there. `spfy/ci/build_gui_linux.sh` derives the triple from
`dpkg --print-architecture` instead, which asks the userland that has to run it.

**armv7 cannot be built either obvious way.** Debian multi-arch is blocked:
`libwebkit2gtk-4.1-dev:armhf` needs `gobject-introspection:armhf`, which needs
`python3:armhf`, and those are not co-installable on an amd64 root. apt reports
only "held broken packages". Building natively under QEMU is worse: measured
here, apt alone ran past 30 minutes before rustup started. What works is
`mmdebstrap --variant=extract`, which unpacks an armhf sysroot without running
a single maintainer script, measured at 31.5 seconds, after which an ordinary
cross build links against it. A sysroot is only headers, shared objects and
pkg-config files; nothing in it has to execute on the build machine.

**A cross build still needs a host compiler.** Cargo builds every proc-macro
and `build.rs` for the host even in a cross build, so without `build-essential`
alongside `crossbuild-essential-armhf` the first crate dies with
"linker `cc` not found", which reads like a cross-compilation fault and is not
one.

A fifth, specific to extracted sysroots: Debian's `-dev` shared-object symlinks
are absolute, so inside a sysroot they resolve against the host root. ld then
cannot see `libdbus-1.so`, silently falls back to `libdbus-1.a`, and fails on
that archive's own systemd dependency. `symlinks -cr` on the sysroot fixes it;
`-lsystemd` is also passed explicitly.

### Why not musl

The two musl tarballs are statically linked so they run on Alpine and in
`FROM scratch` containers with no libc question at all. Alpine ships
`webkit2gtk-4.1-dev` but no static archives, and WebKitGTK is not practically
statically linkable anywhere, so a GUI there could only be a dynamically linked
binary needing GTK, WebKit and roughly 40 other shared objects present on the
target. That is the opposite of the property those legs exist to provide, and a
`FROM scratch` container has no display in any case. Every other Linux user has
a glibc leg above with the GUI in it.

## How it ships

Built by `.github/workflows/build-installer.yml`, inside the existing engine
jobs rather than a workflow of its own.

**Windows**, both arches, in `build-windows`:

1. `cargo build --release --locked`, with `--target i686-pc-windows-msvc` added
   on the x86 leg. The two arches land in different cargo directories, so the
   verify step below checks the right path per leg.
2. `objdump -f` asserts the machine type against `matrix.guiArch`, the same
   check the SAPI DLLs get. An x86_64 exe compiles into the x86 installer
   without a murmur from Inno and then refuses to start for every 32-bit user,
   so this is asserted rather than assumed.
3. `spfy_gui --self-check` runs against the just-built engine and the repo's own
   voice folders. This is the real gate: it resolves the engine, lists voices,
   synthesises, then synthesises the same sentence wrapped in
   `<prosody rate="x-slow">` and requires the tagged arm to be at least 1.5
   times longer. "It compiled" and "the window opened" both prove nothing, and
   before the SSML pass existed the tagged arm was longer too, because the
   engine read the tags out loud.
4. `/DWithGui` goes to `iscc`, which adds the exe, the Start Menu entry, the
   `App Paths` registration, the optional desktop icon and the finish-page
   Launch Speechify checkbox.

**Linux**, in `build-unix`, through `spfy/ci/build_gui_linux.sh` in a second
container. It is usually the same image as the engine's, but on linux-x86 it is
deliberately `i386/debian:bookworm` against the engine's amd64, because there
is no usable i386 webkit on an amd64 root. The script enforces the same
`SPFY_MAX_GLIBC` ceiling the CLI is held to, since a GUI needing a newer glibc
than the engine beside it would fail silently on exactly the machines the CLI
still worked on.

**macOS**, in `build-unix`, one `cargo build` with no container and no
dependency install, because Tauri uses the system WKWebView.
`MACOSX_DEPLOYMENT_TARGET` is passed and read back off the linked binary, for
the same reason `build_unix.sh` does it for the CLI: unset, the binary silently
demands whatever macOS the runner happens to be.

The packaging step then adds the platform's own entry point. macOS gets
`Speechify.app`, assembled by hand rather than by Tauri's bundler, and
self-contained: `spfy_synth` is copied into `Contents/MacOS` rather than
symlinked to `bin/`, because a user drags the app to /Applications and any
relative link back into the extracted tarball would dangle. Linux gets
`install-desktop.sh`, which writes `~/.local/share/applications/speechify.desktop`
at run time; the tarball is relocatable and `Exec=` has to be absolute, so the
file cannot be shipped ready-made. `--uninstall` reverses it.

The Inno `[Files]` entry has no `skipifsourcedoesntexist`. If the cargo build
silently produced nothing, the compile fails rather than shipping a Start Menu
shortcut that points at a missing file. Inno cannot tell a 32-bit exe from a
64-bit one, so the arch check in step 2 is the only thing standing between a
mismatched `GuiDir` and a broken installer. Compiling the ISS by hand with
`/DGuiDir` runs without that check.
